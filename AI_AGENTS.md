# AI components and boundaries

LLM calls are server-side, JSON-schema constrained, timeout/retry bounded, and logged as `agent_actions`. They receive untrusted content as quoted data and no credentials. If validation fails, the UI asks the user/merchant to clarify; it never guesses.

| Component | Purpose, inputs, outputs | Allowed tools/actions | Prohibited and deterministic dependency/failure handling |
|---|---|---|---|
| Catalog Intelligence | Maps prescribed CSV fields and optional description text to typed attribute *proposals*. Input: validated row/text. Output: normalized key/value, confidence, source spans, warnings. | read parsed upload; propose normalization | Cannot publish, create prices/stock, or overwrite facts. Catalog validator checks type/range; ambiguous/missing values become readiness issues, not data. |
| Policy Intelligence | Summarizes policy text into a human-reviewable structured-rule proposal. Output: clause source, rule proposal, confidence. | read policy text; propose fields | Cannot activate policies or infer missing commercial rules. JSON-schema and merchant approval gate all rule changes; on failure retain original text and request structured form. |
| AI Readiness Analyzer | Explains deterministic rubric results and issue remediation in plain language. Input: rubric outputs/evidence only. | read assessment, formulate explanation | Cannot score, resolve issue, or apply a fix. Readiness service calculates score; unsupported explanation falls back to templates. |
| Preference Extraction | Extracts budget, attributes, and ambiguity from customer phrasing. Output: schema-valid preference proposal and clarification need. | read current session; propose preferences | Cannot select product or set unmentioned preference. Validator checks supported keys/values; ask fixed clarification questions on failure. |
| AI Buyer (orchestrator) | Conversationally decides whether to clarify, search, explain or initiate guarded checkout. | read current session, call approved internal read tools, request clarification | Cannot call Razorpay, write catalog/policies, bypass confirmation, or finalize a transaction. The server workflow—not model text—selects permitted operation and validates state. |
| Recommendation Explanation | Explains already-ranked results using supplied snapshots, trade-offs and policy facts. | read recommendation snapshot | Cannot reorder, make unsourced claims, claim stock/payment success, or recommend excluded product. Template fallback displays calculated reasons. |

There are no “payment agent,” “inventory agent,” or scoring agent: normal deterministic services are safer and clearer. The deterministic catalog search applies filters; ranking calculates scores/tie-breakers; readiness rubric calculates points; guardrail service evaluates rules; payment service verifies HMAC/webhook signatures and transitions state. Each tool response has a minimum schema: `request_id`, `version`, `facts[]`, and `warnings[]`; the LLM can only cite these facts.
